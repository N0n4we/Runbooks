# 反模式：把变更集合压成固定构建目标

## 核心原则

**按目录接收变更的流程，必须先定义“哪些变更对象对应哪些执行目标”，不能因为当前只有一个样本，就把目标写成常量。**

本案例的问题不是 GitHub Actions 的 `paths` 语法，也不是文件叫 `Dockerfile` 就一定错误。`paths` 只给出“是否启动”的布尔结果；真正缺失的是启动之后从**变更文件集合**到**应构建镜像集合**的映射。把这一步省略，再把第一个镜像写死，会让单样本验证通过，却使流程的实际处理范围小于它的触发范围。

同样的反模式也可能出现在“目录有变化就运行固定一套测试”“配置有变化就只部署固定服务”等流程中。要审计的是输入与目标的契约，不是某个 CI 语法元素本身。

## 案例：PI Agent 镜像的目录级工作流

来源：`N0n4we/Tools` 的提交 `6e50c63d`，涉及 `.github/dockerfile/Dockerfile` 和 `.github/workflows/pi-agent-image.yml`。

最初的需求同时提到了**一个具体镜像**（预装 PI Agent）和**一个目录级触发条件**（`.github/dockerfile/` 变化后构建、推送）。仅凭这些文字，至少有两种需要区分的契约：

1. 目录专供 PI Agent 使用；目录内相关文件变化，都重建同一个镜像。
2. 目录是多个镜像 Dockerfile 的存放处；哪个 Dockerfile 变更，就构建哪个镜像。

当时没有确认目录的长期用途和变更到构建目标的映射，就直接采用了第一种实现。后续用户明确要求 `<镜像名>.dockerfile` 命名，并只构建该提交中变更的 Dockerfile，说明预期是第二种。**不能倒过来声称原始文字已毫无歧义地规定了矩阵构建；失误在于没有识别并澄清这处会改变架构的歧义。**

原工作流的关键部分是：

```yaml
on:
  push:
    branches: [main]
    paths:
      - .github/dockerfile/**

# build-and-push 的固定输入与输出；省略其他步骤
with:
  context: .github/dockerfile
  file: .github/dockerfile/Dockerfile
  push: true
  tags: |
    ghcr.io/<owner>/<repo>/pi-agent:latest
    ghcr.io/<owner>/<repo>/pi-agent:sha-<commit>
```

这里的 `paths` 正确表达了“目录有变化时启动”，但后续构建始终指向同一个文件和镜像。原实现并没有读取变更文件列表，也没有扫描目录挑选目标；它直接把所有满足触发条件的事件映射到 PI Agent。

可以把两个契约写成：

```text
原实现：目录中存在任意变更 → 构建固定 Dockerfile → 推送固定 pi-agent 镜像
预期：  取得本次变更文件 → 筛出有效 Dockerfile → 每个文件构建并推送对应镜像
```

首次推送时目录里只有 PI Agent 的 Dockerfile，工作流成功发布镜像。这是**单元素输入下的偶然一致**，不能证明集合处理逻辑存在。

## 行为矩阵：单样本为什么掩盖错误

下表按用户后来明确的“只构建变更的镜像”契约比较；未更改的原始 `Dockerfile` 暂视为 PI Agent 的文件。

| 本次目录变更 | 预期构建 | 原实现会做什么 |
| --- | --- | --- |
| 只有原 `Dockerfile` 变化 | PI Agent | 构建 PI Agent；唯一看起来正确的样本 |
| 新增或修改 `other.dockerfile`，原文件仍在 | `other` | 仍构建 PI Agent；目标镜像未发布 |
| 原 `Dockerfile` 与 `other.dockerfile` 同时变化 | PI Agent 和 `other` | 只构建 PI Agent；漏掉一个目标 |
| 只改目录中的说明文件 | 无镜像 | 仍构建并推送 PI Agent |
| 将原 `Dockerfile` 更名为 `pi-agent.dockerfile` | PI Agent | 工作流仍指向旧路径，构建失败 |

这不是“文件名不够好看”的问题。固定文件路径、固定镜像名和目录级触发共同形成了错误的数据流：**事件可以来自任何文件，执行目标却永远是常量。**

## 根因与影响

### 1. 在设计前省略了关键的范围问题

“目录变化后构建”并没有自动回答“构建什么”。单镜像目录可以选择固定目标；多镜像目录则需要按变更选择目标。两种契约要求不同的命名、触发粒度和验证用例。

当这个问题会改变工作流结构时，应先确认，或明确声明自己采用哪种假设并取得认可，而不是因当前只看见一个 Dockerfile 就把目录定义为单镜像目录。

### 2. 把集合输入压成常量输出

目录级事件面对的是零个、一个或多个有效 Dockerfile 的变更集合。原实现完全跳过了“识别集合”和“逐项映射”两步：

```text
变更事件 → 布尔触发 → 固定文件 → 固定镜像
```

因此增加第二个 Dockerfile 时，不是“工作流还没支持新镜像”，而是原有工作流已经会对这个文件的变化做出**错误动作**：触发后重建并推送无关镜像。只把镜像名做成变量、或只把文件改名，都不能单独修复这个错位。

### 3. 验证只覆盖了自己硬编码的特例

本地 `docker build`、`actionlint` 和一次成功的 GitHub Actions 运行分别证明 Dockerfile 可构建、工作流语法有效、固定 PI Agent 路径可发布。它们都没有验证：

- 新镜像的文件变化是否发布新镜像。
- 同一提交中多个 Dockerfile 变化是否各构建一次。
- 没有 Dockerfile 变化时是否不推送任何镜像。
- 删除或重命名时是否避免引用已不存在的文件。

成功的单样本端到端测试不能替代对输入域的验证。不要把“运行成功”写成“需求已完整实现”。

### 4. 发布副作用不只是多花一次构建时间

对于无关变更，原工作流会重新推送 PI Agent 的 `latest` 和以该提交命名的 SHA 标签，而真正变更的镜像没有发布。即使构建结果恰好相同，发布记录也会让排查者花时间辨认“这个提交到底改了哪个镜像”。若基础镜像或依赖在两次构建之间变化，无关事件还可能产生新的 PI Agent 构建结果；这属于风险，不能在没有证据时说它已经发生。

## 更合理的处理方向

### 先确定目录契约，再选择实现

- **若目录确实只服务一个镜像**：可以保留固定构建目标，使用专用 Dockerfile 或明确的专用目录；触发范围应与“哪些文件会影响这个镜像”一致。标准名 `Dockerfile` 在此并无问题。
- **若目录存放多个镜像**：先定义文件到镜像的稳定映射，例如 `<镜像名>.dockerfile`；再从实际变更中选出目标，而不是在工作流中维护一个固定 PI Agent 常量。

`context: .github/dockerfile` 是 Docker 构建上下文，不是构建目标选择器。即使上下文仍是这个目录，也可以只对变更的 Dockerfile 启动构建；不要把“传入目录作为 context”和“扫描或构建目录中所有 Dockerfile”混为一谈。

### 多镜像目录需要显式的数据流

```text
触发条件：.github/dockerfile/ 中有变更
    → 用 gh 获取约定范围内的变更文件
    → 筛选仍存在、名称合法的 *.dockerfile
    → 由文件名得到镜像名
    → 为每个目标生成 matrix 项
    → 逐项 build-and-push；无目标则跳过
```

要明确“约定范围”是**当前 commit**，还是**这次 push 的全部 commits**。GitHub Actions 的 push `paths` 针对整个 push 判断；如果选用 `gh api .../commits/$GITHUB_SHA`，后续筛选只覆盖头提交。若业务要求整次 push，需使用 `before...after` 比较范围，不能让触发和目标发现悄悄观察不同范围。

筛选时要处理删除、重命名、合法镜像名和多文件变更；从 API 取得的文件名也不应未经校验就拼进 shell 命令。具体使用 `gh`、`jq` 或其他工具是实现手段，核心契约是**每个有效变更目标恰好对应一个构建目标**。

## 验证与 Review 检查清单

不能只做语法检查和单镜像成功构建。至少用上面的行为矩阵验证目标集合，再检查实际镜像标签：

- [ ] 目录专供一个镜像，还是承载多个镜像？这个假设是否已得到确认？
- [ ] 触发范围、变更发现范围和构建范围是否一致？
- [ ] 每个文件如何映射到镜像名？这个映射是显式契约还是写死的首个样本？
- [ ] 只改其他镜像时，是否不会推送 PI Agent？
- [ ] 多个 Dockerfile 同时变化时，是否各自产生一个正确目标？
- [ ] 非 Dockerfile 变更、删除和重命名分别如何处理？
- [ ] 单 commit 与整次 push 的范围是否一致且有测试覆盖？
- [ ] “CI 成功”验证的是固定样本，还是完整输入域？

## 审计结论如何表述

不要只写“`paths` 不能提供变更列表”或“`Dockerfile` 应改名”。更准确的结论是：

> 该工作流以 `.github/dockerfile/**` 为触发范围，却将构建文件和 GHCR 镜像固定为 PI Agent。目录中出现第二个镜像文件时，它的变更会触发工作流，但实际发布仍是 PI Agent；单镜像成功运行没有覆盖这条路径。应先确认该目录是一镜像还是多镜像入口；若为后者，需要建立变更 Dockerfile 到镜像目标的一一映射，并验证零个、一个、多个目标的行为。

## 最小记忆规则

```text
目录级触发 + 固定执行目标 + 只验证当前唯一文件
    → 先问：目录是单对象的构建上下文，还是多个对象的入口？
    → 若是后者，不要让首个样本成为整个流程的常量。
```
