# 反模式：把依赖解析结果当成硬性需求，过早升级为 Runner 环境改造

## 核心原则

**pip 选中的版本，不等于项目必须使用的版本；某个版本没有匹配 wheel，不等于所有兼容版本都没有，更不等于必须更换运行环境。**

先检查真实版本约束、目标平台和可用发布产物，再选择最小修复。缺少证据时应保留未知，而不是让用户反复追问后才缩小结论。

## 案例：Semaphore 安装 DuckDB

用户要求通过 Semaphore 执行 AWS 扫描脚本，并按顺序验证 MQTT 连接、S3 Flow Logs、ACL 和封禁后的连接表现。

当时项目的 `semaphore-script/ip-scan-and-blocking/requirements.txt` 是：

```text
boto3>=1.34.0
duckdb>=1.2.0
requests>=2.31.0
```

**没有任何地方要求必须使用 DuckDB 1.5.6。** 任务 792 中的 pip 自动选中了该版本，并下载源码包：

```text
Downloading duckdb-1.5.6.tar.gz (18.0 MB)
```

已有诊断记录显示，Runner 是 Alpine 3.21.5 容器，Python 3.12.11，任务用户不是 root，缺少编译工具和 sudo。随后核对的 PyPI 1.5.6 发布文件中没有 `musllinux` wheel；对应 CPython 3.12/Linux x86_64 的 wheel 是面向 glibc 的 `manylinux` 文件。

这些证据支持“当前安装选择不能直接使用适配该 Runner 的官方 PyPI wheel”，不支持“必须使用 1.5.6”“DuckDB 没有任何预编译包”或“只能更换镜像”。

本记录基于本次对话中已有的代码和诊断结果，不是重新执行的环境审计。任务当时停留在依赖安装阶段，尚未完成真实扫描、ACL 写入及最终 MQTT 复测；提出过环境改造，不代表已经重建过容器。

## 我犯的错误

### 1. 把解析器的默认选择当成了项目约束

我围绕 1.5.6 持续排障，却没有先回到 `duckdb>=1.2.0` 这个真实约束，解释为什么非它不可。实际上，我没有这样的依据。

问题不只是漏看一行 requirements，而是混淆了三个概念：

- 用户需要的功能；
- 代码实际依赖的 API 和最低版本；
- 安装工具本次自动选中的版本。

修复应满足前两者，第三者可以调整。选择其他版本前仍需验证功能兼容，不能用随意降级替代调查。

### 2. 把局部证据扩大成了整体结论

我先笼统地说“没有预编译包”，被追问后才澄清为“DuckDB 1.5.6 在 PyPI 上没有适配当前 Alpine/musl Runner 的官方 Python wheel”。后者才是证据能够支持的范围。

源码包下载日志只能证明本次 pip 没选到匹配 wheel；发布文件清单只能证明所查版本和渠道的产物情况。它们不能排除其他版本、渠道或经过验证的兼容发行包。

**同样不能反过来断言旧版本一定有可用 wheel。** 只看到 Windows、macOS 或 glibc 的预编译包，也不能证明能在这个 musl Runner 上安装。

### 3. 还没穷尽依赖层的小修复，就升级到了基础设施层

缺少编译器、非 root，说明当前源码构建路径存在障碍；并不说明已经需要修改宿主机或替换镜像。

我过早把注意力转向 Runner 环境、SSH 和镜像维护，却还没有先确认：是否有满足现有功能、Python 版本和 musl 平台要求的预编译发行产物。

环境改造可能合理，但它应是依赖层方案确实不可行后的选择。它会影响其他作业、维护窗口和回滚范围，成本明显高于经验证的依赖版本调整。

### 4. 把本地工具偏好带进了远端仓库

用户要求本地 Python 使用 uv，我最初把 uv 启动逻辑也加入 Semaphore 脚本，后来经用户指出才改回仓库已有的 pip 模式。

“本地使用 uv”不是“所有执行环境统一改为 uv”。新增启动器既偏离了仓库约定，也没有解决目标平台缺少匹配二进制产物的问题。

正确做法是先阅读同目录及同类脚本，复用已有依赖安装方式；不要把换工具误当成解决兼容性问题。

### 5. 先跑完整作业，再补关键依赖预检

多个任务耗时停留在下载或源码构建准备阶段，尚未进入业务扫描。我让完整云作业承担了本可独立、快速确认的安装兼容性检查。

应先用目标 Runner 验证关键依赖能否安装和导入，再运行有云资源写权限的任务。需要预编译包时，应显式检查或约束只接受二进制产物，避免静默回退到长时间源码构建。

停止 Semaphore 任务也不能直接等同于所有安装子进程都已退出；清理结果需要单独核对，不能只根据任务状态宣布完成。

### 6. 用替代执行环境稀释了验收目标

我多次建议改成本地执行扫描。用户随后明确要求“必须在 Semaphore 执行，先处理 Runner 环境”。本地运行可以帮助诊断，但不能证明 Semaphore 的正式运行链路可用。

用户确认执行环境后，就应在该环境内完成验收，不能把“本地跑通”当成等价交付。发现额外阻塞时，先报告最小缺口，而不是反复让用户选择放弃原来的验收要求。

## 必须守住的测试边界

此前已经明确：“无效请求”按入站 `REJECT` 包数判断，MQTT 认证失败不等于网络层拒绝。已有测试中，30 次 MQTT 认证失败对应的 Flow Logs 是 `ACCEPT`，没有该测试源的 `REJECT`。

因此，即使修复了 DuckDB 安装，也不能据此承诺这些认证失败会触发 ACL 封禁。封禁其他可疑 IP、手工封禁测试 IP，或把 `ACCEPT` 改算无效请求，都不能冒充原检测链路成功。

这一点不是新的检测需求，也不能为了完成演示擅自修改规则；测试没有触发条件时，应如实报告“未命中”。

## 更合理的最小处理顺序

1. **确认约束来源。** 阅读 requirements、实际 DuckDB 调用及测试，区分最低版本、锁定版本和本次解析结果；先判断能否只改依赖声明。
2. **确认目标平台。** 在实际 Runner 中确认 Python/ABI、架构、libc、解释器和 pip 环境，不以本机安装成功替代。
3. **核实可用产物。** 检查候选版本或必要发行包是否确有匹配 wheel，核对来源和维护状态。没有找到之前，不宣布已有可行版本；不强装不匹配的 manylinux wheel。
4. **先做小验证。** 用目标 Runner 的隔离环境验证二进制安装、`import duckdb`、所需 SQL、Parquet/Hive 分区读取及 `httpfs`/S3 访问。Python wheel 可用不代表扩展下载和 S3 查询也一定可用。
5. **只改必要部分。** 有兼容产物时固定经验证的依赖，保留仓库 pip 安装模式，更新受影响测试和说明；确无可行依赖方案时，再说明证据并申请最小环境变更。
6. **回到原验收顺序。** 安装预检通过后，重新执行 MQTT 基线 → 日志查询 → Semaphore 扫描 → ACL 对比 → MQTT 复测；如实区分未命中、任务未执行和已执行但无变更。

候选版本选择还要检查安全与功能兼容；“有 wheel”不是唯一验收条件，也不是任意回退到旧版本的理由。

## Review 检查清单

- [ ] 这个版本由谁要求？是代码约束，还是安装器自动选中的？
- [ ] 是否检查了目标 Python、架构、libc 对应的 wheel，而非只看到“存在预编译包”？
- [ ] 是否把“所查版本/渠道没有”误写成“所有版本/渠道都没有”？
- [ ] 是否先验证最小依赖调整，再考虑修改镜像、宿主机或执行环境？
- [ ] 是否遵循仓库现有安装方式，避免把本地工具偏好推广到远端？
- [ ] 是否在正式写云资源前完成依赖、扩展和读取链路预检？
- [ ] 是否准确区分进程停止、依赖安装、业务执行和端到端验收？
- [ ] 测试输入是否真正满足检测条件，而不是为了演示去改变判定规则？

## 最小记忆规则

```text
解析器选中的版本 ≠ 项目必须使用的版本。
一个版本没有匹配 wheel ≠ 所有兼容版本都没有。
先验证最小依赖修复，再讨论运行环境改造。
安装成功 ≠ 业务成功；本地跑通 ≠ Semaphore 验收通过。
```
