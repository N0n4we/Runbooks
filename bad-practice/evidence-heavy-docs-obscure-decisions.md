# 反模式：用证据堆砌和重复免责声明代替清晰的评估文档

## 核心原则

**评论记录结论和关键证据；评论外记录字段／tag 变更计划；必要的证据边界集中说明。**

可追溯不等于把调查材料全部贴进正文，谨慎不等于每段重复免责。好的评估让负责人快速看懂：哪个版本受影响、业务是否满足利用条件、为什么这样分诊，以及证据覆盖到哪里。

## 案例：27 条 Dependabot 漏洞评论草稿

用户提供两条参考评论，要求采用固定七段结构。首次调整虽然满足了段落数量和顺序，却没有学习示例的信息密度：依赖链罗列多个父包和锁文件链接；检查段重复环境限制与未知项；证据基线又重述调查过程和未执行事项。重写后文档体量反而增大。

为了避免把未执行的字段修改说成事实，正文还反复出现“拟设为”“尚未执行”。这个顾虑本身合理，错误在于没有划清**评论正文、变更计划和执行记录**的边界，导致读者要从过程说明中寻找结论。

本案例讨论的是草稿编写质量，不以生成文件或通过格式检查证明评论已发布、字段已更新或漏洞已修复。

## 反模式的表现与代价

| 表现 | 为什么有问题 | 应保留什么 |
| --- | --- | --- |
| 只复制七段顺序 | 形式一致，信息仍然散乱 | 每段承担一个明确职责 |
| 依赖链堆砌父包、版本范围和链接 | 关键引入路径与修补建议被淹没 | 关键链路、锁文件证据、版本命中、目标版本 |
| 检查段混写入口、条件和调查过程 | 无法快速理解可达性依据 | 业务入口、受影响 API／输入、利用前提、环境边界、Reachability |
| 证据基线重复日期、commit、来源和所有核对步骤 | 来源说明变成调查流水账 | 固定版本、实际核对的材料、必要的等级差异说明 |
| 到处写“拟”“尚未执行” | 字段计划与漏洞评估混在一起 | 评论外的旧值 → 新值与执行条件 |
| 以段落数、链接数作为质量验收 | 检查了形式，却漏掉重复和难读 | 同时检查事实、结构和阅读负担 |

这些问题批量复制到 27 条记录后，审阅者要反复过滤同样的说明，更容易漏掉真正不同的利用前提、修复版本和审批要求。

## 根因

1. **把材料完整性当成正文完整性。** 调查需要保留足够材料，但交付正文只需要支持结论的关键证据；详细链路和补充材料可以留在审阅区或证据附件。
2. **把谨慎写成重复免责声明。** 同一个未知项在检查、基线、末段重复出现，没有增加可信度，只增加阅读成本。
3. **先批量套模板，后考虑读者。** 模板保证外形一致，却不会自动判断一句话是否必要。自动校验不能代替对照范文的编辑审阅。

## 更合理的写法

### 1. 先定义每段职责，再填材料

漏洞分诊评论可以沿用以下七段，不必为了显得规范添加小标题和解释性括号：

1. 接手人、分诊结论、优先级与风险决定。
2. 关键依赖链、版本命中与修补建议。
3. 已检查业务入口、利用条件、环境边界与可达性判断。
4. 上游公告、Severity 与 CVSS。
5. 证据基线、实际核对材料及等级差异。
6. 归属、指派、状态与适用的修复验证范围。
7. 静态证据边界、验证与审批要求、修复引用及期限状态。

固定的是信息职责，不是所有漏洞共用同一个结论。

### 2. 精简最容易膨胀的三个段落

以下为表达模板，不是真实评估或执行记录：

```text
依赖链：<父包@版本 → 受影响包@版本>，见<锁文件链接>。版本命中公告，建议升级至 <修补版本> 或兼容的更高修复版本。

已检查的业务入口为 <源码链接>。<输入来源／API 与利用条件的关系>。<未确认的关键范围>，因此 Reachability 为 <有依据的判断>。

证据基线为 <仓库与固定 commit>，并核对 <实际查看的告警／公告／源码>。<原始载荷或规范化字段的等级差异及处理依据>；保留原始载荷作为来源记录。
```

- 一个链接能证明的事实，不为“完整”再贴三个同类链接；不同副本或不同入口确实影响结论时再补充。
- 不必逐条展开所有父依赖，但必须保留受影响副本共存、跨主版本兼容或暂无补丁等会改变处置的事实。
- 检查段先写已查到什么，再写利用需要什么，最后给出判断；不要反复论证“没有搜到不等于不存在”。
- 没有检查发布包源码，就不能套用范文的“已核对 npm 包源码”；看过 Dockerfile 也不能写成已核验线上镜像。

### 3. 把字段／tag 计划放在评论边界之外

正文不应承担执行清单的职责。每条草稿可在评论结束标记后附一小块代码框，明确不发布：

```text
字段／tag 变更计划（不属于评论；未执行）
来源字段：列出 sync-data 的旧值 → 新值，并保留原始载荷。
Project 字段：列出 Owner Team、Status、Risk Decision、验证与审批字段的旧值 → 新值。
Assignees：当前账号 → 经确认的目标账号；无需变更则写“不变”。
Issue labels：列出实际增加／移除的标签；无需变更则写“不变”。
执行条件：明确评论发布与字段修改的授权范围；执行前回读。
```

Project 字段、Assignees 和 Issue labels 不是同一类对象，不能笼统写“改 tag”而省略具体目标。评论提及账号也不等于完成指派。

### 4. 精简措辞不能改变事实

把计划移出评论，不代表可以直接把目标状态写成已经发生的事实。草稿中若采用配套变更完成后的口吻，必须在审阅区说明发布前提，并在发布前核对；若只获准发表评论，就不能声称未执行的字段更正已经完成。

同样不能为了短而丢掉会改变结论的边界：搜索无命中不等于不可达，静态分诊不等于复测通过，低优先级不等于低 Severity，普通 Medium 的审批规则不能机械套到 High。

### 5. 批量前先做代表性样稿

先选择一条普通依赖、一条存在真实业务调用的漏洞和一条特殊项（如无补丁），对照范文检查信息密度，再推广到整批。模板里的共有句只写必要内容，逐条差异必须留在正文。

## Review 检查清单

- [ ] 能否快速找到“版本、利用条件、判断、修补建议”？
- [ ] 依赖链是否只保留影响结论的路径和副本？
- [ ] 检查段是否把实际发现、推断与未知范围区分清楚？
- [ ] 证据基线是否说明实际核对材料，而不是复述调查流水账？
- [ ] 相同限制是否在多个段落重复？删除后是否仍能准确理解证据边界？
- [ ] 字段／tag 计划是否在评论边界外，且可从旧值追踪到目标值？
- [ ] 正文中的“已更正”“设为”“保持”等表述，发布时是否有真实依据？
- [ ] 是否保留特殊修补边界、环境前提及真实审批要求？
- [ ] 除格式、链接和版本校验外，是否实际对照范文检查了简洁性？

## 最小记忆规则

```text
结论先行，证据够用，边界明确，计划外置。
规范化不是增加篇幅；谨慎不是重复免责；短文不能牺牲事实。
```
