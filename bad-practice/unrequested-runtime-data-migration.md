# 反模式：未经确认，把一次性数据迁移塞进运行时启动流程

## 核心原则

**更换存储实现，不等于获准在启动时自动迁移旧数据、删除旧表。数据如何搬迁、何时执行、何时清理源数据，应作为独立决策明确确认。**

需要保留已有数据，但不能以“保护数据”为理由，擅自选择自动迁移策略；也不能为了减少代码，直接忽略旧数据。

## 案例：pi-durable 接入 durable-bash

用户要求：

> 使用 @stablemodels/durable-bash 将 just-bash 文件系统适配到 Cloudflare DO，然后把文件都放到 just-bash 文件系统，给 pi-durable 启用 bash 工具。

需求涉及文件存储切换与文件搬迁，但没有明确指定“部署后首次启动自动迁移”，也没有明确确认删除源数据表。

当时的实现额外在 `src/bash/files.ts` 的 `AgentFiles` 构造函数中加入：

```text
DO 实例化
  → 检查 hermes_text_files 是否存在
  → 在同步事务内搬迁全部旧文件，保留路径、文本和 ETag
  → 成功后 DROP TABLE hermes_text_files
  → 冲突或异常时回滚，并抛出构造异常
```

交付时将其描述为“自动迁移”。用户追问后才明确：这是程序内新增的一次性兼容逻辑，迁移成功后，后续 DO 实例化只剩旧表存在性检查。

记录范围是本地实现与评审，不是线上事故：当时仅完成本地测试和构建 dry-run，未部署或执行线上数据迁移。

## 为什么这是坏实现

### 1. 把实施方式当成了已确认需求

“把文件放到新文件系统”没有决定迁移应当手动执行、随发布执行，还是由首次访问触发。实现者自行补上了迁移时机、执行范围和源表清理策略。

提前宣布计划，不等于这些新增决策已获得确认；事务和测试也不能替代授权。

### 2. 把一次性运维工作绑进长期运行路径

正常启动不仅初始化当前存储，还承担旧数据搬迁和清理职责。迁移完成后，这段逻辑不再提供正常业务能力，却继续留在每次实例化的路径上，增加维护负担。

问题不只是“多了一次查询”，而是长期运行代码需要继续理解已经完成的历史切换过程。

### 3. 隐式改变了启动和回滚语义

- 激活 DO 就可能触发数据写入和旧表删除，业务访问与迁移操作没有明确分界。
- 迁移冲突会使构造函数抛错，阻止 DO 正常启动；事务回滚能保护数据，却不能保证服务可用。
- 成功删除旧表后，回滚到只读取旧表的代码版本，不能直接读取已搬迁的文件。新表中的数据仍在，但代码回滚不等于数据格式回滚。

这些是实现引入的风险，不是本案例中已发生的线上故障。

### 4. 用实现正确性替代决策正确性

精确保留文本、ETag、事务回滚和重复启动测试，能证明某些迁移行为按代码设计执行；不能证明这个设计是用户选择的迁移方式。

**测试覆盖了额外功能，不会把额外功能变成必要需求。**

## 更合理的处理方式

1. **先确认现状与方式。** 是否存在需要保留的旧文件？是否要支持旧部署直接升级？用户希望手动迁移，还是明确接受自动迁移？
2. **将存储接入与数据迁移分开。** 正常运行代码负责当前文件系统和业务能力；确需手动迁移时，再提供最小、显式的一次性步骤或命令，而不是默认加入通用兼容框架。
3. **单独确认源数据清理。** 迁移完成并验证后，按确认的回滚安排决定何时删除旧表。复制数据不等于获准清理源数据。
4. **准确交付。** 区分“迁移能力已实现”“迁移已执行”“源数据已清理”，不能笼统说“文件已迁移”。

若用户明确要求自动升级迁移，它可以是合理实现，但仍需明确触发时机、失败行为、数据清理和回滚策略。反模式是未经确认自行加入，而不是自动迁移本身。

必要的当前存储初始化、ETag 和限额保护不应因为本次反思一起删除；它们与旧数据搬迁不是同一项职责。

## Review 检查清单

- [ ] 需求要求了旧数据迁移，还是我自行假定需要兼容旧部署？
- [ ] 是否明确确认了迁移时机、范围与执行方式？
- [ ] 构造函数、启动钩子或首次读取是否隐藏了数据搬迁、删除或清理？
- [ ] 数据迁移完成后，这段代码是否还需要留在正常运行路径？
- [ ] 迁移失败是否会阻止原本无关的服务启动？
- [ ] 清理源数据是否获得确认，代码回滚后能否读取已有数据？
- [ ] 测试是在验证用户需要的行为，还是在为额外加入的功能提供正当性？

## 最小记忆规则

```text
存储切换 ≠ 启动时自动迁移 ≠ 删除旧数据。
先确认迁移策略，再实现；一次性运维工作不要默认永久留在运行时。
事务和测试保证执行正确，不替用户决定是否执行。
```
