# 反模式：用 rescue 和状态标记模拟跨 play 的 finally

## 核心原则

**资源清理应有明确的生命周期边界，不应仅为走到清理步骤，就先将失败标记为已恢复，再依赖后续阶段重新制造失败。**

本案例的主要反模式是：

- **Catch-and-continue / deferred failure**：捕获错误后继续执行，在另一个阶段延迟报错。
- **Flag-based error handling**：把原生失败状态转换为手工维护的变量，再重建失败结果。
- **Temporal coupling**：前面阶段的正确性依赖后面某个检查一定执行。

这里不是禁止 `block/rescue`、`set_fact` 或失败汇总。需要审计的是：**没有实际恢复动作、没有明确的 best-effort 业务契约，却为了清理资源而接管框架原有错误语义的实现。**

## 案例：日志下载失败后关闭 SSH 转发

来源：`cloud-cap/semaphore-script` 的一次修复迭代，主要涉及：

- `ansible_scripts/download_logs_v4.yaml`
- `ansible_scripts/download_logs_v5.yaml`

原有流程大致是：

```text
Agent 开启 SSH 转发
    → Agent / EMQX 节点采集日志
    → 控制机打包上传
    → Agent 关闭 SSH 转发
```

原问题是：开启转发后，如果采集任务失败，后面的关闭步骤可能无法执行。

**原来并不缺少错误输出。** Ansible 默认输出失败任务及模块返回的错误，并返回失败状态；项目还通过 `callback_plugins/simple_logger.py` 记录失败主机、任务名和错误信息到 `/tmp/semaphore/logs/ansible_results.log`。

修复中新增了类似下面的处理。这是简化示意，不是完整可执行 playbook：

```yaml
# 前面的采集 play
- block:
    - set_fact:
        log_download_ok: false

    - name: Collect logs
      include_tasks: tasks/compress_and_fetch_directory.yaml

    - set_fact:
        log_download_ok: true

  rescue:
    - set_fact:
        log_download_error: "{{ ansible_failed_task.name }}: {{ ansible_failed_result.msg }}"
```

然后在另一个 Agent 收尾 play 中读取这些变量：

```yaml
# 后面的收尾 play
- block:
    - assert:
        that:
          - hostvars[item].log_download_ok | default(false) | bool
          - hostvars[item].log_download_error | default('') == ''
      loop: "{{ download_hosts }}"

  always:
    - include_tasks: tasks/disable_tcp_forwarding.yaml
```

这使错误传播变成：

```text
采集失败
    → rescue 执行成功，Ansible 认为该失败已被恢复
    → 用主机变量保存失败状态 / 文本
    → 继续运行其他 plays
    → 后续 assert 读取变量并重新失败
    → assert 所在块的 always 关闭转发
```

这套实现可以通过限定范围内的普通任务失败测试，不能据此说它必然误报成功。问题在于：本来只需要保障资源清理，现在却增加了一套跨 play 的失败状态协议。

## 为什么需要审计

### 1. rescue 没有恢复业务，只是在保持流程继续

`rescue` 中如果只有 `set_fact`、`debug` 或其他必然成功的记录动作，原始故障实际上并未消除。

成功执行 `rescue` 后，Ansible 可以继续执行，并不再仅因这个已被处理的失败而返回非零退出码。为了保持失败语义，代码又不得不在别处主动 `fail` 或 `assert`。

**“日志里出现过 fatal”不等于“最终任务一定失败”。** 两者必须分别验证。

### 2. 错误处理依赖远处的检查点

前面的 `rescue` 是否安全，取决于后面的汇总是否：

- 一定会执行，而不是被提前退出、条件分支或执行范围限制跳过。
- 覆盖所有相关主机和阶段。
- 不会读到被后续成功阶段覆盖的状态。
- 能区分“成功”“失败”和“根本没有执行”。

例如，同一主机同时属于 `agent0` 和 `agent1` 时，后续阶段设置 `log_download_ok: true`，不应抹去前面阶段的失败。为解决这种问题继续叠加错误变量，正是手工状态协议膨胀的信号。

### 3. 重复维护错误信息，改变最终失败位置

原始错误本来已经由 Ansible 和日志回调输出，再保存任务名和 `msg`、跨 play 汇总、重新触发断言，会增加维护成本。

最终失败可能显示在 Agent 上的 `assert`，而实际故障发生在某个 EMQX 节点的筛选或压缩任务。原始日志仍在，但最终失败主机、任务位置与真实故障位置不再一致。

若仅保存 `msg`，还可能丢失汇总所需的 `stderr`、返回码等上下文；这不意味着原始日志消失，而是说明新建的错误表示未必与原生结果等价。

### 4. 后续 play 有 always，不等于整个流程有 finally

示例中的 `always` 实际保护的是**后面的结果检查块**，不是前面的开启转发与日志采集全过程。

能否进入这个 `always`，仍取决于前面各 play 的执行路径。因此审计时不能只搜索到 `always:` 就认定清理已获保障。

Ansible 的 `always` 不能直接跨多个 plays 包裹完整流程；主机不可达、无效任务定义或执行进程被终止等情况，也不在普通任务失败的同等保证范围内。

### 5. 小型清理修复演变成额外编排

本案例迭代中还曾加入 `hosts: emqx:localhost` 等占位主机模式，让 localhost 跳过远端任务，从而避免整个批次全员失败 / 不可达造成的提前终止。该做法后来撤回。

这不是 `:localhost` 自带容错能力，而是利用额外参与者改变执行器的退出条件。它是一个值得追问的配套信号：**是否在绕过执行器行为，而不是明确资源的清理责任？**

localhost 合理地承担控制机任务并不是反模式。需要警惕的是仅为让执行器继续运行而添加的占位参与者，以及为此不断增加的状态、分支和辅助编排文件。

## 更合理的处理方向

### 优先保留原生错误传播

如果资源获取、所有依赖该资源的操作、资源释放能够位于同一个受保护作用域，应优先使用真正覆盖该生命周期的 `block/always` 或外层 `try/finally`。

概念上应当是：

```text
try:
    获取资源
    执行所有需要该资源的工作
finally:
    释放资源
```

不为了打印日志而增加 `rescue`。在没有成功 `rescue` 掩盖原始失败的情况下，`always` 成功执行也不会自动把原始任务失败变成成功。

### 跨 play 时，先确认边界，不要机械添加 always

- 不要把关闭转发直接放进 Agent 日志采集块的 `always`：后续 EMQX 下载可能仍需要这个跳板。
- 不要假设可以把多个 plays 或 `import_playbook` 直接塞进任务级 `block`。
- 如果完整生命周期无法纳入同一保护边界，应先明确可靠性要求，再决定是否调整外层调度、独立执行清理，或接受并记录有限保证。
- 涉及编排边界调整时，应先说明改动范围并取得认可，而不是把小修复悄悄扩展为新框架。
- 不可达或进程终止时若也要求自动恢复，需要另行设计超时回滚、资源租约或外部检查机制，不能只靠 `always` 承诺实现。

### 不要仅删变量，留下吞错逻辑

看到这份文档后，**不能只删除错误标记或最终断言，却保留成功执行的 `rescue`**。这样可能把失败任务变成成功。

如果暂时保留跨 play 的延迟失败协议，应将其作为有明确边界的折中：保留必要失败状态、验证完整路径、沿用原有详细日志，而不是再建一套日志系统。把错误文本换成布尔标记只能减少重复，不能消除跨阶段耦合。

## 不应误判的合理场景

以下使用方式不应仅因出现 `rescue` 或错误汇总就被判为坏实践：

- `rescue` 确实完成重试、回滚或备用方案，业务恢复后允许继续。
- 批处理明确要求 best-effort：独立任务尽量执行，最后统一报告全部结果。此时聚合结果本身就是业务契约，而不是为了绕到清理步骤的临时补丁。
- 明确设计的工作流系统，用结构化阶段结果和统一出口管理状态，并有对应测试和责任边界。
- 收集失败上下文用于告警，但并未接管或丢失原生失败状态。

本次另一个修复——日志采集使用独立临时目录，并在采集块的 `always` 中清理本次目录——不属于这个反例。它没有通过 `rescue` 消化错误，目录的使用与清理也在同一受保护块中；即使中断后留下目录，下次也不会复用它。

## Review 检查清单

- [ ] 原生执行器和已有回调是否已经能输出错误？新增代码实际解决的是日志问题、失败状态问题，还是清理问题？
- [ ] `rescue` 是否执行真实恢复？如果只有 `set_fact` / `debug`，为什么要将失败视为已处理？
- [ ] 是否形成“失败 → 标记 → 继续 → 远处检查 → 重新失败”的链条？
- [ ] 继续执行是否有明确的 best-effort 业务要求，还是仅为到达清理步骤？
- [ ] 最终失败检查若被跳过，会不会让任务误报成功？
- [ ] 是否覆盖全部主机和阶段？状态会不会被后续成功操作覆盖？
- [ ] 是否分别验证了原始错误输出、最终退出码、最终失败归属？
- [ ] `always` 真正包住的是资源生命周期，还是仅包住后续断言 / 汇总？
- [ ] 清理是否发生在资源最后一次使用之后？会不会提前关闭仍在使用的跳板？
- [ ] 是否依赖占位主机、清除失败状态或忽略错误等额外技巧，才能走到收尾？
- [ ] 是否清楚区分普通任务失败与 unreachable、进程终止等边界？
- [ ] 清理自身失败时，是否仍返回失败并保留原始错误上下文？
- [ ] 小修复是否引入了与需求不相称的状态管理和文件拆分？
- [ ] 简化实现时，是否避免了“只删最终检查、保留吞错 rescue”？

## 搜索入口与验证方法

可以先搜索这些信号，但**搜索命中不是缺陷证据**：

```bash
rg -n 'rescue:|always:|set_fact:|ansible_failed_(task|result)|hostvars\[|log_download_(ok|error)|ignore_errors:|clear_host_errors|hosts:.*:localhost' <待审计目录>
```

随后画出真实控制流，至少用隔离环境注入以下故障：

| 场景 | 需要核对的结果 |
| --- | --- |
| 开启资源过程中部分成功后报错 | 是否尝试释放可能已经获取的资源；最终是否失败 |
| 采集任务、显式 setup 或压缩失败 | 原始错误可见；普通失败路径上清理执行；最终非零退出 |
| 全部采集主机发生普通任务失败 | 是否仍能按设计到达清理，而非只验证单主机成功样本 |
| 同一主机前一阶段失败、后一阶段成功 | 前一阶段的失败是否被覆盖 |
| 清理自身也失败 | 采集错误和清理错误均可诊断，最终不能成功 |
| 主机不可达、执行被终止 | 实测并记录保证边界，不能从普通失败测试外推 |

不要仅检查控制台出现过 `fatal`，也不要仅检查最终返回非零；还要确认清理是否执行、是否操作了正确主机、是否晚于资源的最后一次使用。优先使用临时目录、模拟任务和本地执行器测试，避免为了审计直接修改生产 SSH 配置。

## 审计结论如何表述

不要只写“使用了 rescue，所以是坏实践”。应指出具体链条与影响，例如：

> 此处 rescue 未恢复业务，只将原始失败写入主机变量并继续执行。任务最终失败依赖另一 play 的断言，而该断言的执行路径与清理生命周期并未形成统一保护边界。请说明这种延迟失败是否为明确的业务要求，并验证遗漏、覆盖或跳过结果检查时的行为；若仅为确保清理，应优先明确资源的收尾责任，避免重新实现错误传播。

若现有测试已证明限定范围内行为正确，应如实记录。维护性风险与已经复现的误报成功、漏清理缺陷应分开报告，不要把设计异味直接夸大为所有失败路径都不可靠。
